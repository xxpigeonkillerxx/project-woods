# Research requests ("Research this" button)

The atlas is a static site, so its buttons can't start research by themselves. Instead:

1. Every county header and township card has a **Research this** button (or **Research again** when a record exists). It opens a pre-filled GitHub issue from `.github/ISSUE_TEMPLATE/research-request.yml` with the `research-request` label. Greg presses **Submit**.
2. A scheduled Claude run (a few times a day, no paid API key, no GitHub Action calling Claude) lists open issues with that label and works through them oldest first.
3. For each request it follows the runbook below, opens a PR, merges it once `validate` passes, and closes the issue with a short summary comment.

## Runbook for the scheduled run

For each open `research-request` issue, oldest first, at most 3 per run (leave the rest for the next run):

1. **Claim it.** Comment that research has started (with the footer below). Skip issues that already have a "started" comment from an earlier run less than 24 hours old, unless no PR followed.
2. **Read the request.** Issue fields: County, Township (blank = whole county), Census GEOID, Atlas record id (blank = no record yet), and an optional focus question.
3. **Research** with `docs/SWEEP_PLAYBOOK.md`:
   - Official sources only (county, township, district health department, State of Michigan). Every finding gets a `sources.json` entry with the section and a short quote in `note`.
   - Unzoned does **not** mean camping is allowed. `camping_outlook` stays `unverified` unless an ordinance or official written answer addresses camping.
   - Never invent findings, drive times, property details or boundaries. Anything not readable (scanned PDF, blocked host) is listed as a follow-up, not guessed.
   - Fetch pages with `curl` (through the proxy). If a host is blocked, propose adding that exact official host to the environment allowlist; don't route around the network policy.
4. **Contacts stay private.** Clerk/zoning contacts go only to the private project file `outreach/contacts.csv` (outside this repo). Never put emails, phone numbers or private names in the repo, the PR or the issue. `validate.mjs` blocks emails and phone numbers.
5. **Records.** Update or add the record in `data/townships.json` (new records: run `scripts/link-geoids.mjs` for the GEOID), add sources, and write or extend `docs/research/<county>.md`. Run `node scripts/validate.mjs`.
6. **PR.** Branch, commit, open a PR whose body says `Closes #<issue>`, and merge it once the `validate` check passes (Greg approved merging on green). If the check fails, fix it; never skip validation.
7. **Close the issue** with a summary comment: what changed (outlook, zoning, key limits), the PR link, what couldn't be read, and suggested next questions for the township.
8. If nothing official could be found, still close the issue with what was tried and what's left, and don't open an empty PR.

Comments posted by the run end with:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```
